# Live chat

Every chat is named by a `chat_id`, a UUID that says who is in it. Each level only talks to the level right above and below it:

| `chat_id` | Chat | Its people (they read, write and receive) |
|---|---|---|
| a child's id | the child's chat | the child's **PADRE**, the **DOCENTE** of the child's salon, the **ADMIN** of the child's estancia |
| a DOCENTE's user id | DOCENTE ↔ ADMIN | that docente and the **ADMIN** of their estancia |
| an ADMIN's user id | ADMIN ↔ ORG | that admin and every **ORG** user |

So the app's screens use: Admin → Org: the admin's own id. Admin → Teacher X: X. Teacher → Admin: the teacher's own id. Org → Admin A: A.

ORG **reads** every chat (REST history), but only writes in and receives the ADMIN ↔ ORG ones. Any other id, or a chat you are not in, is a `404`.
Messages are **sent** over a WebSocket, **read** (history) and **deleted** over REST.

| What | How |
|---|---|
| Send, live delivery | `WS /ws/chat` (this page; WebSocket routes are not in OpenAPI) |
| History, oldest first | `GET /messages?chat_id=&since=` (`since`: timestamp with timezone, see below; `include_deleted=true`: ORG only) |
| Delete (soft) | `DELETE /messages/{id}`: **only in a child's chat**, by the child's PADRE or the estancia's ADMIN, any message of it |

Rules: messages are never edited. DOCENTE ↔ ADMIN and ADMIN ↔ ORG messages are never deleted (`403`). Photos and avisos work in every chat.
A chat whose child or docente / admin is archived is read-only (`409`).

## Connecting

`Authorization: Bearer <session token>` on the handshake (OkHttp: `Request.Builder().header(...)`). The token is checked like any REST call
(valid, not pending, role has `message:read`). If it isn't, the server accepts and closes with code **4401**: refresh the token (`POST /auth/refresh`) and reconnect.
When the server is ready it sends `{"type":"ready"}`; messages are delivered from then on.

The session token lasts 5 minutes and so does the socket's authentication: before it expires send `{"type":"auth","token":"<fresh token>"}` (same user)
and the server answers `{"type":"auth_ok"}`. Otherwise it closes with **4401** at expiry. Role, salon or child changes apply on the **next message**,
because access is read from the database for every frame.

## Frames (JSON, one object per text frame)

| Direction | Frame |
|---|---|
| client → server | `{"type":"message","id":"<uuid>","chat_id":"<uuid>","content":"Hola","sent_at":"2026-05-01T09:30:00Z","is_aviso":false,"attachment_file_id":null}` |
| server → sender | `{"type":"ack","id":"<uuid>","created":true,"message":{...MessageOut}}` |
| server → sender | `{"type":"error","id":"<uuid>"|null,"status":403|404|409|422|429,"detail":"..."}` (the socket stays open) |
| server → the others | `{"type":"message","message":{...MessageOut}}` (every device of every participant except the one that sent it) |
| server → participants | `{"type":"deleted","id":"<uuid>","chat_id":"<uuid>"}` |

`MessageOut` carries `chat_id` (never `child_id`), so the client knows which chat a frame belongs to.
| both | `{"type":"ping"}` → `{"type":"pong"}` |

**Keepalive:** send a `ping` about every 30 s. A socket with no frame for 90 s (`CHAT_IDLE_SECONDS`) is closed with code **4408**, so a phone that lost its connection stops counting as online (and gets pushes instead); just reconnect and catch up with `since`. The same ping keeps Cloudflare/nginx from dropping an idle connection.

`id` is generated by the client and makes sending **idempotent**: sending the same message again (offline queue retry) is acked with
`created:false` and not delivered twice; a different body under the same id is a `409`. Messages the client sent while the socket was down are simply sent again after reconnecting;
after reconnecting it catches up with `GET /messages?chat_id=...&since=<created_at of the newest message it has>`: `since` filters on the time the **server** stored the message (`created_at`), not on the client's `sent_at`, so messages sent late from an offline phone aren't skipped. Messages deleted while it was away are not listed there; refetch the whole chat now and then to drop them (the socket has no replay).
Limit: 60 messages per minute per user.

## Avisos and photos: marker lines

The stored `content` is plain text. In every frame and in `GET /messages` the server appends **marker lines** at the end of `content`, in this order:

1. `::Aviso` when the message is an aviso (`is_aviso: true`).
2. `::Image /<file id>.<ext>` when it carries a photo.

A message with no text is just its markers. For example an aviso with a photo:

```
Junta el viernes
::Aviso
::Image /0b8e...-....jpg
```

The client strips the markers from the end (first `::Image`, then `::Aviso`). `is_aviso` and `attachment_file_id` are still in the message as fields.

## Photos

Upload with `purpose: MESSAGE_ATTACHMENT` and `target_id` = the **chat id**, by anyone who can write in that chat. A photo can only be sent in the chat
it was uploaded for (otherwise `422`), and only that chat's people (plus ORG) can download it.

```mermaid
sequenceDiagram
  participant A as Sender
  participant API
  participant S3 as RustFS / S3
  participant B as Recipient
  A->>API: POST /files (purpose MESSAGE_ATTACHMENT, target_id = chat id)
  API-->>A: signed PUT url
  A->>S3: PUT bytes
  A->>API: POST /files/{id}/complete
  A->>API: WS message with attachment_file_id
  API-->>B: WS message, content ends with "::Image /{file id}.jpg"
  B->>API: GET /files/{file id}
  API-->>B: signed GET url
  B->>S3: GET image
```

The client takes the uuid from the `::Image` line and asks `GET /files/{id}` for the signed URL.
The extension is only informative. One photo can be attached to one message.

## Limits

* The hub of connected sockets is in memory: **run a single uvicorn process** (no `--workers`). Several processes/containers would need a shared
  fan-out (Postgres `LISTEN/NOTIFY` or Redis) behind `app/chat/hub.py`; `NOTIFY` does not store anything, so history still comes from `GET /messages`.
* The proxy in front (Cloudflare / nginx) must pass WebSocket upgrades (`Upgrade` and `Connection` headers; nginx `proxy_http_version 1.1`, a long `proxy_read_timeout`).
  The app needs `uvicorn[standard]` (it brings `websockets`).
* Participants with no socket open get a push notification, see [push.md](push.md).
* `CORS` doesn't apply to sockets; the app isn't a browser, so there is no origin check.
